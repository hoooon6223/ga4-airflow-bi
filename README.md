# GA4 Merch Shop 운영 대시보드 — BigQuery · dbt · Airflow

GA4 raw 이벤트를 dbt로 운영 지표 마트로 만들고, Airflow가 매일 아침 **품질 게이트를 통과한 날에만** 대시보드를 게시하는 파이프라인입니다.

**대시보드**: https://hoooon6223.github.io/ga4-airflow-bi/

핵심은 자동화 자체가 아니라, 운영 담당자가 **믿고 판단할 수 있는 숫자**입니다. 그래서 지표를 로그 단위부터 정의했고, 수집이 깨진 날은 숫자 대신 "검수 실패"를 보여 줍니다.

---

## 1. 왜 만들었나

Google Merchandise Store(구글 굿즈 쇼핑몰)의 **운영 담당자**가 매일 아침 전날 매출을 확인하고, 지표가 흔들리면 직접 원인을 분석하는 상황을 가정했습니다.

대시보드는 매일 아침 세 가지 질문에 차례로 답합니다.

1. **어제 매출이 평소 범위 안인가**: 지난주 같은 요일, 최근 7일 평균과 비교
2. **벗어났다면 어디서 변했나**: 매출 = 세션 × 주문 전환율 × 객단가, 기기별, 신규/재방문별
3. **이 숫자를 믿을 수 있나**: 품질 체크 6종의 판정(정상 / 경고 / 차단)

**마케팅 효율 대시보드가 아닌 이유**: GA4 export에는 광고비가 없어서 ROAS·CAC를 계산할 수 없습니다. 대신 운영 대시보드는 "무엇이(대시보드) → 어디서(지표 구조) → 왜(분석)"로 분석 프로젝트에 이어집니다.

## 2. 데이터와 운영 기간

`bigquery-public-data.ga4_obfuscated_sample_ecommerce` 데이터는 이미 웨어하우스(BigQuery)에 들어 있는 GA4 원본 export입니다. 날짜별 테이블이 92개(2020-11-01 ~ 2021-01-31) 있고, 이벤트 1건이 1행입니다. 그래서 별도 적재(E, L) 없이 BigQuery 안에서 SQL로 변환(**ELT**)합니다.

데이터를 직접 확인해 보니 수집이 깨진 구간이 두 개 있었습니다.

| 구간 | 무엇이 깨졌나 | 처리 |
|---|---|---|
| 11/1 ~ 11/29 | 11/1~11/10 구매의 100%에 거래번호가 없음. 장바구니 이벤트 0건이었다가 11월 말까지 불안정 | 제외 |
| 1/25 ~ 1/31 | 구매 이벤트가 빈 껍데기(거래번호·매출·상품 정보 없음). 구매 세션의 60.8% → 100% | 제외 ([사고 기록](docs/04_incident_0126.md)) |
| **11/30 ~ 1/24** | 수집 온전, 8주(56일), 사이버먼데이 포함 | **운영 기간** |

> 결함 구간을 보정해서 쓰면, 담당자가 수집 문제를 실제 매출 변화로 오해할 수 있다고 판단했습니다. 결함 구간은 raw와 staging에 남기고 KPI에서만 뺐습니다.

## 3. 지표 정의 (요약)

전체 정의와 분자·분모는 [지표 정의서](docs/02_metric_definitions.md)에 있습니다.

| 지표 | 정의 | 왜 이렇게 |
|---|---|---|
| 주문 | 거래번호 1개 = 1건. 같은 거래번호는 처음 찍힌 이벤트만 | GA4는 이벤트 로그라 새로고침하면 구매가 다시 찍힘 |
| 매출 | 주문별 `purchase_revenue` 합 (USD, 세금·배송비 제외, 환불 미반영) | 상품 매출 합과 0.05% 이내로 일치 |
| 주문 전환율 | 주문 ÷ 세션 | 세션 × 전환율 × 객단가 = 매출이 정확히 성립 |
| 퍼널 | 세션 → 상품 조회 → 결제 시작 → 구매 세션 (도달 기준) | 결제의 24%가 장바구니를 거치지 않음 → 장바구니는 결제 막대를 "경유 / 바로 결제"로 나눠 표시 |
| 쪼개 보는 기준 | 신규/재방문, 기기 | 재방문 전환율이 신규의 5.6배라 구성 변화만으로 전환율이 움직임. 기기는 장애 위치 찾기용 |

**세션 기준으로 쪼갠 이유**: 기념품 쇼핑몰이라 재구매(리텐션)보다 방문이 구매로 이어지는 전환이 핵심이라고 판단했습니다.
**채널을 쓰지 않은 이유**: 주문 세션의 58%가 자기 사이트 도메인 referral로 기록돼 있어서, 채널로 쪼개도 의미 있는 변화가 보이지 않습니다.

## 4. 품질 게이트

| # | 체크 | 판정 | 기준 (초기값) |
|---|---|---|---|
| DQ1 | 원천 도착 / 이벤트 총량 | 차단 | 0건, 또는 7일 기준선 대비 < 0.3 |
| DQ2 | 거래번호 없는 구매 **세션** 비율 | 경고 / 차단 | ≥ 20% / ≥ 40%, 해당 세션 ≥ 5 |
| DQ3 | 이벤트별 수집량 (조회·장바구니·결제·구매) | 경고 | 7일 기준선 대비 < 0.1 |
| DQ4 | 주문 매출 vs 상품 매출 차이 | 경고 | > 2% |
| DQ5 | 다중 주문 세션 비율 | 경고 | ≥ 25%, 5세션 이상 |
| DQ6 | 집계 대사 (구분별 합 = 전체, 매출 항등식) | 차단 | 불일치 |

- 기준값은 운영 기간의 날짜별 분포와 알려진 사고 사이에 두었습니다. 예를 들어 DQ2는 평소 최대가 14.3%, 사고 첫날이 60.8%입니다. 근거는 [정의서](docs/02_metric_definitions.md#기준값-근거-2026-11-25-dbtanalysesdq_calibration_dailysql)에 있습니다.
- **판정은 그날까지의 데이터만으로** 합니다. 그날 아침에는 하루짜리 이상인지 며칠 이어질 결함인지 알 수 없기 때문입니다.
- 차단된 날은 KPI 대신 **"검수 실패" 페이지**를 게시하고, 그 날은 비교 기준에서도 자동으로 빠집니다.

## 5. 아키텍처

```text
GA4 raw (BigQuery 공개 데이터)
   │  Airflow  ga4_ops_daily  매일 07:00 KST, 데이터 하루씩
   ▼
check_raw      BigQueryTableExistenceSensor (10분 간격, 최대 6시간 대기)
dbt_run        stg_events → f_orders · f_sessions → dq_daily → kpi_daily · kpi_weekly
dbt_test       품질 게이트 (error = 차단, warn = 경고)
render_ok      마트를 직접 조회해 정적 HTML 생성 (탭: 개요 / 퍼널·구분 / 데이터 품질)
render_blocked 위 단계 중 하나라도 실패하면 "검수 실패" 페이지 생성
publish        gh-pages 브랜치에 push → GitHub Pages (브랜치 이력 = 날짜별 게시 기록)
gate_result    차단되었거나 게시가 실패하면 실행을 빨간색으로 남김
```

| dbt 모델 | 1행 = | 용도 |
|---|---|---|
| `stg_events` | 이벤트 1건 | 배열을 한 번만 펼침. 결함 구간 포함 전 기간 보관 |
| `f_orders` | 주문 1건 | 담당자의 직접 분석용. 현업이라면 원천을 주문 DB로 바꿀 자리 |
| `f_sessions` | 세션 × 날짜 | 퍼널 단계 도달 여부, 주문·매출 |
| `kpi_daily` / `kpi_weekly` | 날짜(주) × 구분 | 대시보드. 지난주 같은 요일·7일 평균 비교 포함 |
| `dq_daily` | 날짜 × 체크 | 품질 판정과 진단 정보 |
| `data_incidents` (seed) | 결함 구간 | 비교 기준에서 자동 제외 |

## 6. 도구 선택

자세한 의사결정 기록(ADR)은 [설계 문서 §5](docs/01_design.md)에, 이전 버전과의 비교는 [여기](docs/05_vs_github_actions.md)에 있습니다.

| 영역 | 선택 | 고른 이유 |
|---|---|---|
| 웨어하우스 | BigQuery | GA4가 원본을 자동으로 보내 주는 곳. 다른 웨어하우스는 옮기는 단계만 늘어남 |
| 변환 | dbt Core | 테스트 심각도 warn/error가 경고/차단 게이트에 그대로 대응. `insert_overwrite`로 재실행해도 결과가 같음. 정의서를 코드 옆에 둠 |
| 오케스트레이션 | Airflow (로컬 Docker) | 백필·catchup, 작업 의존성, 재시도, 날짜별 실행 이력. 이전 버전(GitHub Actions)에서 예약 실행이 4~5시간 밀렸고 백필이 없었음 |
| 대시보드 | 정적 HTML (Power BI 스타일) | 게이트를 통과한 날에만 게시되고 차단일엔 "검수 실패". BI 도구는 테이블에 실시간으로 붙어 있어서 차단돼도 숫자가 보임 |

## 7. 과거 데이터로 "매일 도는" 모습 만들기

데이터는 2020~2021년에 멈춰 있지만 Airflow는 실제 달력으로 돕니다. 그래서 날짜를 일정 간격만큼 밀어서 대응시켰습니다.

```text
데이터 날짜 = 2021-01-11 + (실행일 − 운영 시작일 2026-11-27)

DAG를 켠 날 (11/26)  → 11/30 ~ 1/10 (42일)을 catchup으로 백필  → 42/42 성공, 42분
11/27 ~ 12/10 매일 07:00 KST → 1/11 ~ 1/24 (14일) 라이브
```

백필과 라이브가 같은 DAG, 같은 코드로 돕니다.

## 8. 검증

| 검증 | 결과 |
|---|---|
| staging이 raw와 같은가 | 92일 모두 날짜별 행 수 일치 (4,295,584행) |
| 마트가 설계 때 직접 조회한 숫자를 재현하는가 | 운영 기간 주문 3,232 · 매출 $221,762 · 세션 230,471 · 구매 세션 2,903, 기기·신규 분해까지 일치 |
| 같은 날을 다시 돌려도 같은가 | dbt 재실행, Airflow "Clear" 재실행 모두 합계 불변 |
| 백필 결과 | 11/30~1/10: 주문 2,642 · 매출 $182,560 · 세션 175,174 — staging에서 독립 재계산한 값과 일치 |
| 게이트가 사고를 막는가 | 1/26 재현 → DQ2 60.8%로 차단, 검수 실패 페이지만 생성, 실행 빨간색 ([기록](docs/04_incident_0126.md)) |
| 원천이 안 오면 | 없는 날짜(2/1)로 시험 → Sensor가 다시 확인하다 기한 초과 → 검수 실패 페이지 |

라이브 14일이 끝나면(12/10) 56일 전체를 위 기준 숫자와 다시 대조합니다.

## 9. 한계

- **주문 DB가 없습니다.** 현업에서는 매출·주문은 주문 DB, 행동(세션·퍼널)은 GA4를 기준으로 하고 거래번호로 연결합니다. 여기서는 GA4를 매출 기준으로 썼습니다.
- 정보가 빠진 구매(평소 구매 세션의 약 4~5%) 때문에 주문·매출이 그만큼 **과소 집계**됩니다. 추정해서 채우지 않았습니다.
- 사용자 식별이 브라우저 쿠키 기준이라, 재방문은 실제보다 적게 잡힙니다.
- 품질 기준값은 56일과 사고 한 번으로 정한 **초기값**입니다.
- 로컬 Docker라 노트북이 꺼져 있으면 정시에 돌지 않습니다(켜면 catchup으로 따라잡음).

## 10. 실행 방법

```bash
# 1) dbt (로컬)
python3 -m venv .venv && .venv/bin/pip install dbt-core==1.12.7 dbt-bigquery==1.12.4
cd dbt && GCP_KEYFILE=~/.gcp/<key>.json ../.venv/bin/dbt build --profiles-dir . --vars '{run_date: "2020-12-17"}'

# 2) Airflow (Docker)
cp airflow/.env.example airflow/.env      # 키 경로, 운영 시작일, GitHub 토큰 입력
git clone --branch gh-pages https://github.com/hoooon6223/ga4-airflow-bi.git .pages
cd airflow && docker compose build airflow-init && docker compose up -d   # http://localhost:8080
```
