# 이전 버전(GitHub Actions)과의 비교

같은 데이터(GA4 Merch Shop), 같은 목적(운영 담당자가 매일 아침 보는 대시보드)으로 먼저 만든 [`ga4-ops-bi`](https://github.com/hoooon6223/ga4-ops-bi)와 이 프로젝트를 비교한다.
"Airflow를 써 봤다"가 아니라, 앞 버전을 운영하면서 부딪힌 문제가 무엇이었고 무엇을 얻고 잃었는지 적는다.

## 한눈에

| 항목 | 이전: GitHub Actions + Python + SQL | 지금: Airflow + dbt |
|---|---|---|
| 실행 시각 | cron `17 22 * * *` (07:17 KST). **실제로 4~5시간 늦게 시작된 적이 있음** (이전 저장소 워크플로 주석에 기록) | Airflow 스케줄러가 07:00 KST에 실행. 첫 라이브 실행은 07:04에 끝남 |
| 처리할 날짜 결정 | 상태 기반: "마지막으로 적재된 날 + 1" | 달력 기반: 실행 날짜에서 데이터 날짜를 계산 (`데이터 날짜 = 1/11 + (실행일 − 운영 시작일)`) |
| 과거 날짜 재처리 (백필) | 날짜를 하나씩 `--date`로 넣어 수동 실행 | DAG를 켜면 catchup으로 42일을 순서대로 자동 처리 (42/42 성공, 42분) |
| 변환 | SQL 파일 01~05를 한 트랜잭션으로 실행. 파티션 삭제·삽입을 직접 작성 | dbt 모델. `insert_overwrite`로 파티션 교체, `ref()`로 실행 순서 자동 계산 |
| 품질 판정 | 마지막 SQL에서 `RAISE` → Python이 문자열을 읽어 차단 판단 | dbt 테스트 심각도: `warn` = 경고, `error` = 차단. 기준값은 `dq_daily` 한 곳에 |
| 차단된 날 | 트랜잭션 롤백 → **아무것도 적재·게시하지 않음**. 같은 날을 다음 실행에서 다시 시도 → 결함이 고쳐질 때까지 **뒤 날짜도 멈춤** | 그날 KPI는 적재하되 차단으로 표시 → **"검수 실패" 페이지를 게시** → 다음 날은 계속 진행. 차단일은 비교 기준에서 자동 제외 |
| 원천 미도착 | 도착 확인 후 바로 차단 | `BigQueryTableExistenceSensor`가 10분마다 확인하며 최대 6시간 대기 |
| 실패 알림 | 실패한 워크플로 = GitHub 실패 메일 | 실패 콜백(로그, Slack 확장 가능) + 실행이 빨간색으로 남음. 게시 실패도 빨간색 |
| 실행 이력 | 워크플로 실행 목록 + 날짜별 산출물 커밋 | 날짜·작업별 상태, 재시도, 로그를 Airflow 화면에서 확인. "Clear"로 특정 날만 재실행 |
| 게시 기록 | `outputs/runs/<날짜>` CSV와 HTML 커밋 | gh-pages 브랜치의 날짜별 커밋 (CSV 없이 마트 직접 조회) |
| 운영 비용·부담 | 무료, 서버 없음 | 로컬 Docker. 무료지만 **노트북이 켜져 있어야** 정시 실행 |

## 무엇 때문에 옮겼나

1. **정시성**: 매일 아침 보는 대시보드인데, 예약 실행이 몇 시간씩 밀리면 의미가 줄어든다. GitHub Actions의 예약 실행은 시작 시각을 보장하지 않는다.
2. **백필**: 정의를 고치거나 결함을 복구하면 과거 날짜를 다시 돌려야 한다. 날짜를 하나씩 손으로 넣는 방식은 실수하기 쉽다. Airflow는 날짜 범위 재처리와 catchup이 기본 기능이다.
3. **게이트의 위치**: 이전에는 "차단 여부"를 Python이 SQL 에러 문자열을 파싱해서 판단했다. 지금은 dbt 테스트의 심각도와 Airflow 작업 의존성(`dbt_test` 실패 → 다음 작업 중단)으로 표현된다. 판정 로직을 따로 짜지 않는다.
4. **차단된 날의 처리**: 이전 방식은 하루가 막히면 리플레이 전체가 그 날에서 멈췄다. 운영에서는 "어제 숫자는 못 믿지만 오늘 숫자는 봐야" 한다. 그래서 차단일을 기록·표시하고 다음 날은 계속 진행하도록 바꿨다.

## 이전 버전이 더 나았던 점 (포기한 것)

| 항목 | 내용 |
|---|---|
| AI 코멘트 | 이전 버전은 Claude가 숫자를 자리표시로만 쓰는 현상 요약을 붙였다. 이번 프로젝트는 지표 설계와 오케스트레이션에 집중하려고 넣지 않았다 |
| PDF 보관 | 이전 버전은 날짜별 PDF도 남겼다. 지금은 HTML과 gh-pages 이력만 남긴다 |
| 원자성 | 이전 버전은 01~05가 한 트랜잭션이라 반쯤 적재된 날이 생길 수 없었다. 지금은 모델별로 파티션을 교체하므로, 중간에 실패하면 일부 모델만 갱신된 상태가 될 수 있다 (같은 날을 다시 돌리면 정리된다) |
| 운영 부담 | GitHub Actions는 서버가 필요 없다. 지금은 Docker와 노트북 전원이 필요하다. 현업이라면 Cloud Composer나 사내 Airflow로 옮긴다 |
| 대사 항목 수 | 이전 버전은 R1~R6 집계 대사를 매일 했다. 지금은 DQ6(구분별 합 = 전체, 매출 항등식, KPI = 주문 테이블)로 줄였다 |

## 지표 정의에서 바뀐 것

이전 버전의 지표 정의서를 그대로 옮기지 않고, 처음부터 데이터를 다시 보고 정했다.

- **운영 기간**: 이전은 92일 전체를 리플레이했다. 지금은 수집 결함 구간(11월 초 거래번호·장바구니, 1월 말 주문 정보)을 빼고 56일만 쓴다.
- **주문 정의**: 이전은 "거래번호, 없으면 세션+금액"으로 묶었다. 지금은 거래번호만 쓰고, 거래번호가 없는 구간은 운영 기간에서 뺐다. 보조 규칙으로는 중복을 확실히 걸러낼 수 없기 때문이다.
- **품질 지표 단위**: 빈 구매를 이벤트가 아니라 세션으로 센다. 12/30에 이벤트 기준 41%였던 것이 실제로는 2세션의 반복이었다(세션 기준 9.5%).
- **채널**: 세션 채널의 58%가 자기 사이트 referral이라 쪼개 보는 기준에서 뺐다. 대신 신규/재방문과 기기를 쓴다.
