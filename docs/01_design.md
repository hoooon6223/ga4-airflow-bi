# GA4 Merch Shop 운영 대시보드 — 설계 문서

작성일: 2026-11-25
상태: 설계 검토 반영 완료, 오너 승인 대기 (구현 시작 전)
관련 문서: [`02_metric_definitions.md`](02_metric_definitions.md) (지표 정의서, 분자/분모)

이 문서는 구현하는 사람이 작성자에게 다시 묻지 않고 계획을 세울 수 있도록, 지금까지 정한 내용과 그 근거를 모은 것이다. 근거에 쓴 숫자는 모두 2026-11-25에 BigQuery에서 직접 조회한 값이다.

- **[정함]**: 프로젝트 오너가 결정한 것
- **[제안]**: 설계 과정에서 채운 것. 오너가 반대하지 않았지만 명시적으로 고른 것은 아니다
- **[미정]**: 구현 전이나 구현 중에 정해야 하는 것

## 1. 왜 만드는가

### 1.1 목적 [정함]

Google Merchandise Store(구글 굿즈 온라인 쇼핑몰)의 **운영 담당자**가 매일 아침 전날 매출을 확인하고, 지표가 흔들리면 직접 원인을 분석할 수 있게 한다.

대시보드는 매일 아침 세 가지 질문에 위에서부터 순서대로 답한다. [제안]

1. **어제 매출이 평소 범위 안에 있나**
2. **벗어났다면 어디서 변했나**: 매출을 세션 × 주문 전환율 × 객단가로 쪼개고, 기기와 신규/재방문으로 나눠 본다
3. **이 숫자를 믿을 수 있나**: 데이터 도착, 이벤트 누락, 주문 정보 누락, 중복 여부를 확인한다

### 1.2 왜 운영 대시보드인가 (마케팅 효율 대시보드가 아닌 이유)

- GA4 export에는 **광고비가 없다**. 그래서 ROAS, CAC, CPA 같은 효율 지표를 계산할 수 없다.
- 운영 대시보드는 분석 프로젝트로 자연스럽게 이어진다.
  - 대시보드는 **무엇이** 변했는지 보여 준다.
  - 지표 구조는 **어디서** 변했는지 보여 준다.
  - 분석 프로젝트는 **왜** 변했는지 답한다.
  - 운영 기간이 사이버먼데이, 크리스마스, 연말 이후 하락기를 포함해서, 시즌 분석으로 이어 가기 좋다.

### 1.3 보는 사람 [정함]

쇼핑몰 운영 담당자 한 명이다. 매일 대시보드를 보고, 지표가 흔들리면 직접 SQL로 분석한다.

→ 그래서 마트에는 집계 테이블뿐 아니라 **주문 1건, 세션 1건 단위의 사실 테이블**도 두고, 담당자가 직접 쿼리할 수 있게 한다.

### 1.4 하지 않는 것

- ROAS 같은 마케팅 효율 지표는 넣지 않는다. 광고비가 없기 때문이다.
- 유입 채널은 쪼개 보는 기준에서 뺀다 (§4.5).
- 대시보드는 원인을 단정하지 않는다. 원인 판단은 담당자의 분석 몫이다.
- 월별 모니터링은 하지 않는다. 운영 기간이 8주라서 월 단위로는 점이 2개뿐이다.
- 누락된 매출을 추정해서 채우지 않는다. KPI에 추정값을 섞지 않는다.

## 2. 데이터

### 2.1 원천 데이터의 상태

| 항목 | 내용 |
|---|---|
| 위치 | `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*` (읽기 전용) |
| 형식 | GA4 BigQuery Export 원본. 날짜별로 테이블이 따로 있음 (`events_20201101` ~ `events_20210131`, 92개) |
| 단위 | 1행 = 이벤트 1건. `event_params`, `items`는 배열(REPEATED RECORD)이라 UNNEST가 필요함 |
| 갱신 | 없음. 2021-01-31에서 멈춘 고정 데이터 |
| 난독화 | 일부 값이 `<Other>`, `(data deleted)`, `(not set)`으로 가려짐 |
| 사용자 식별 | 로그인 ID 없음. `user_pseudo_id`는 브라우저 쿠키 기준 |

→ 이미 데이터 웨어하우스(BigQuery)에 들어 있는 raw 데이터다. 그래서 웨어하우스 안에서 SQL로 변환하는 **ELT**로 staging과 mart를 만든다. 데이터를 웨어하우스까지 옮기는 단계(E, L)는 GA4 export가 대신한다.

### 2.2 수집 결함과 운영 기간 [정함]

92일을 확인한 결과, 수집이 깨진 구간이 앞뒤에 하나씩 있다.

**11/1 ~ 11/29: 거래번호와 장바구니 수집 결함**
- 11/1~11/10은 구매 이벤트 421건 **전부** 거래번호가 없다(`(not set)` 또는 빈 값). 11/11은 64건 중 36건, 11/12부터는 정상이다.
- 이 구매들은 매출 값과 상품 정보가 있는 실제 주문이다. 같은 세션에 정상 구매가 함께 있는 경우는 0건이다.
- `add_to_cart`는 11/2~11/15에 0건이다. 11/16 이후 다시 찍히기 시작하지만 불안정하다. 주간 이벤트 수 기준으로 `view_item` 대비 4% → 12%다. 11/30이 있는 주부터는 15~26%로 안정된다. 이 수치는 이벤트 수 기준이고, 세션 기준 장바구니 담기율(S01)과는 분모가 다르다.

**1/25 ~ 1/31: 주문 정보 수집 결함**
- 1/26부터 대부분의 구매 이벤트가 빈 껍데기다. 거래번호는 `(not set)`, 매출은 null, 상품명은 `(not set)`, 가격과 수량은 null이다.
- 빈 구매가 있는 구매 세션의 비율은 1/26 60.8%, 1/27 82%, 1/28 91%, 1/31 100%다.
- 1/26~1/31 빈 구매 세션 210개 중 209개가 결제 정보 입력(`add_payment_info`)을 거쳤다. 실제 주문이었지만 정보만 사라진 것으로 보인다.
- 1/25는 거래번호 없는 구매가 13%로 평소보다 높다. 그래서 운영 기간에서 함께 뺀다.

**운영 기간: 2020-11-30(월) ~ 2021-01-24(일), 8주, 56일**
- 수집이 온전한 구간만 쓴다. 결함 구간을 보정해서 쓰면 담당자가 수집 문제를 실제 매출 변화로 오해할 수 있기 때문이다.
- 11/30을 고른 이유는 세 가지다. 장바구니가 안정되고, 사이버먼데이가 포함되고, 월요일이라 주간 집계가 깔끔하게 시작한다.
- 결함 구간은 raw와 staging에 그대로 두고, mart의 KPI와 비교 계산에서만 제외한다. 결함 목록은 dbt seed(`data_incidents.csv`)로 관리한다.

### 2.3 현업과의 차이

- **현업에서는 매출·주문의 기준이 주문 DB다.** GA4는 행동(세션, 퍼널)을 보는 데 쓰고, 거래번호로 두 데이터를 연결한다. "DB 주문 중 GA4와 연결된 비율"이 수집 품질 지표가 된다.
- **이 데이터에는 주문 DB가 없다.** 그래서 GA4를 매출 기준으로 쓴다.
- 이 차이를 구조로 대비한다. 주문 사실 테이블 `f_orders`를 독립된 모델로 두면, 현업에서는 이 모델의 원천만 주문 DB로 바꾸면 된다.
- 전환율과 퍼널은 현업에서도 GA4만으로 계산하는 게 보통이다. 분자와 분모가 같은 방식으로 수집돼야, 누락이 양쪽에 비슷하게 걸리기 때문이다. 그래서 이 부분은 현업 방식과 같다.

## 3. 지표 구조 [정함]

### 3.1 최상위 지표: 매출

```text
매출 = 세션 × 주문 전환율 × 객단가
            (주문 ÷ 세션)  (매출 ÷ 주문)
```

- **왜 세션 기준으로 쪼개나**: 기념품 쇼핑몰이라 재구매(리텐션)보다 방문이 구매로 이어지는 전환이 핵심이라고 판단했다. 데이터로 봤을 때도 재구매 비중이 낮았다(오너 판단. 수치는 산출하지 않았다).
- **왜 주문 전환율 분자가 "주문 수"인가**: 세 항의 곱이 매출과 정확히 같아진다. Universal Analytics의 전자상거래 전환율(거래 ÷ 세션)과 같은 정의다.
  - 주문이 있는 세션 수를 분자로 쓰면, "주문 세션당 주문 수"(약 1.1) 항이 하나 더 필요하다. 11/12~1/31 기준 주문 세션은 4,016개, 주문은 4,438건이다.

### 3.2 퍼널

```text
세션 → 상품 조회 → 결제 시작 → 구매 세션
                    ├─ 장바구니 담고 결제
                    └─ 담지 않고 바로 결제
```

- 퍼널은 하나다. 결제 시작 단계의 막대만 두 경로로 나눠 칠한다.
- 각 단계는 "그 세션이 이 단계의 이벤트를 하나라도 가졌나"로 센다. 단계 간 전환율은 (이 단계 세션 ÷ 앞 단계 세션)이다.
**운영 기간 퍼널** (세션 × 날짜 기준, 마트가 다시 만들어 내야 하는 값)

| 단계 | 세션 | 단계 간 전환율 |
|---|---|---|
| 세션 | 230,471 | |
| 상품 조회 | 46,194 | 20.0% |
| 결제 시작 | 6,192 | 13.4% |
| ├ 장바구니 담고 결제 | 4,710 (76%) | |
| └ 바로 결제 | 1,482 (24%) | |
| 구매 세션 | 2,903 | 46.9% |

- **장바구니를 필수 단계로 넣지 않은 이유**
  - 운영 기간 결제 시작 세션의 24%(1,482개)는 같은 세션에 장바구니 담기가 없다.
  - 참고로 11/30~1/31 기준 분석에서는, 같은 세션에 담기가 없는 구매 세션 중 일부(238개)가 이전 세션에서 담은 경우였다. 나머지 604개(구매 세션의 18%)는 담기 기록이 아예 없었다.
  - 필수 단계로 두면 이 경로가 퍼널에서 사라지거나 전환율이 왜곡된다.
- **남은 단계는 거의 순서대로 이어진다** (운영 기간): 결제 시작 세션 중 상품 조회가 없는 것은 207개(3.3%)다. 구매 세션 중 결제 시작이 없는 것은 7개다.
- **장바구니 담기율**(장바구니 세션 ÷ 상품 조회 세션)은 퍼널 밖 보조 지표로 둔다. 수집 이상 감시에도 쓴다. 운영 기간 평균은 26.8%(12,358 ÷ 46,194)이고, 일별로는 12월 초 약 36%에서 1월 중순 약 20%로 점진적으로 내려간다.
- **퍼널의 "구매 세션"은 주문 수와 다르다.** 운영 기간 구매 세션은 2,903개, 주문은 3,232건이다. 한 세션에 주문이 여러 건일 수 있어서 구매 세션이 약 10% 적다. 두 숫자가 다르다는 것을 화면과 정의서에 밝힌다.

### 3.3 쪼개 보는 기준 [정함]

| 기준 | 값 | 담당자가 답을 얻는 질문 | 결과에 따른 행동 |
|---|---|---|---|
| 신규/재방문 | 신규 = 세션 번호 1, 그 외는 재방문 | 방문자 구성이 바뀐 건가, 사이트 문제인가 | 구성만 바뀌었으면 대기. 신규·재방문 전환율이 모두 떨어졌으면 사이트 점검 |
| 기기 | 데스크톱 / 모바일(태블릿 포함) | 특정 기기에서만 문제가 생겼나 | 해당 기기 담당 개발팀에 전달 |

근거 (운영 기간, 세션 × 날짜 230,471개 기준, 주문 전환율 = 주문 ÷ 세션):

| 구분 | 세션 | 주문 | 주문 전환율 (K04) |
|---|---|---|---|
| 신규 | 172,350 (75%) | 1,125 | 0.65% |
| 재방문 | 58,121 (25%) | 2,107 | 3.63% |
| 데스크톱 | 133,778 (58%) | 1,868 | 1.40% |
| 모바일 (태블릿 포함) | 96,693 (42%) | 1,364 | 1.41% |
| 전체 | 230,471 | 3,232 | 1.40% |

- **신규/재방문**: 재방문의 전환율이 신규의 약 5.6배다. 그래서 구성이 바뀌는 것만으로도 전체 전환율이 움직인다.
- **기기**: 데스크톱과 모바일의 전환율이 거의 같다. 그래서 기기 구성 변화보다는 특정 기기에서 생기는 장애를 찾는 데 쓴다. 태블릿은 세션의 약 2%이고 56일 동안 주문 세션이 약 60개라 모바일에 합친다. 모바일 하루 주문 세션은 평균 약 22개(최소 4개)라 7일 평균 비교를 우선한다.
- **재방문 세션 ≠ 재구매.** 재방문 세션은 "30분 이상 쉬었다가 같은 브라우저로 다시 온 방문"이다. 첫 구매 전의 재방문도 포함한다. 재방문 주문 세션의 이전 세션과의 간격은 1시간 미만 11%, 1시간~1일 39%, 1~7일 22%, 7일 이상 23%, 알 수 없음 5%다. 이 수치는 1,814개 기준인데, 시각 경계를 UTC로 잘라서 위 표의 재방문 구매 세션 1,826개와 약간 다르다.

### 3.4 모니터링 주기와 비교 기준 [제안]

- 매일 본다. 비교 기준은 **지난주 같은 요일**과 **최근 7일 평균**이다. 하루 주문이 수십 건이라 전날과 바로 비교하면 우연한 변동이 크기 때문이다.
- 주간 추세를 같은 화면에 함께 보여 준다.
- 지난주 같은 요일 비교는 12/7부터, 7일 평균은 유효일 5일이 쌓이는 12/5부터 채워진다 (구현 후 확인).
- 결함 구간이나 차단된 날은 비교 기준에서 뺀다.

### 3.5 유입 채널을 쓰지 않는 이유 [정함]

운영 기간 정상 주문 세션 2,907개(기간 내 서로 다른 세션 기준) 중 58%가 자기 사이트 도메인(`shop.googlemerchandisestore.com`, `googlemerchandisestore.com`)에서 넘어온 referral로 기록돼 있다. 또 세션의 28%는 채널 값이 없다. 그래서 채널별로 쪼개도 대부분 의미 없는 칸에서 변화가 나온다.

## 4. 데이터 품질과 품질 게이트

### 4.1 원칙 [정함]

- 품질 체크를 통과해야만 대시보드에 반영한다(품질 게이트).
- **차단**: 숫자 자체를 믿을 수 없는 경우. 그날 KPI를 게시하지 않고 "검수 실패"를 보여 준다.
- **경고**: 숫자는 맞지만 해석에 주의가 필요한 경우. 게시하되 경고를 표시한다.
- 판정에는 **그날까지의 데이터만** 쓴다. 다음 날 이후 데이터는 쓰지 않는다. 그날 아침에는 하루짜리 이상인지 여러 날 이어질 결함인지 알 수 없기 때문이다. DQ1, DQ3처럼 지난 7일과 비교하는 체크도 이 원칙에 맞는다.
- 판정은 전체 기준으로 한다. 기기별·브라우저별 분해와 "몇 명, 몇 세션에 몰렸나"는 진단 정보로만 보여 준다. 기기별로 판정하면 하루 숫자가 작아서 우연히 경고가 뜬다.

### 4.2 체크 목록 [정함]

| # | 체크 | 잡아내는 문제 | 판정 |
|---|---|---|---|
| DQ1 | 그날 raw 테이블 도착 여부, 이벤트 총량 | 데이터 미도착, 반쯤만 도착 | 차단 |
| DQ2 | 빈 구매 세션 비율 | 1월 말 같은 주문 정보 누락 | 경고 / 차단 |
| DQ3 | 이벤트별 수집량 급감 (조회·장바구니·결제·구매) | 11월 같은 특정 이벤트 소실 | 경고 |
| DQ4 | 주문 매출 합계와 상품 매출 합계의 차이 | 금액 수집 이상 | 경고 |
| DQ5 | 주문이 여러 건인 세션의 비율 | 중복 수집, 비정상 주문 | 경고 |
| DQ6 | 집계 대사 (기기별 합계 = 전체, 신규+재방문 = 전체, 퍼널 각 단계 ≤ 앞 단계*) | 우리 SQL의 버그 | 차단 |

\* 퍼널은 도달 여부로 세서 앞 단계를 건너뛴 세션이 있다(결제 시작의 약 3.3%). 그래서 "각 단계 ≤ 앞 단계"는 세션 단위가 아니라, 단계별 세션 수의 합계 크기로만 확인한다. 구현할 때 이 점을 반영해야 한다.

### 4.3 DQ2 기준값 [정함]

**지표** = 거래번호가 없는 구매 이벤트가 1개 이상 있는 구매 세션 ÷ 전체 구매 세션 (세션 기준)

- 분자는 매출 값의 유무와 상관없이 센다. 그래야 1월 말 같은 빈 구매와 11월 초 같은 "매출은 있는데 거래번호만 없는 구매"가 모두 잡힌다.
- 운영 기간에는 "거래번호는 없고 매출은 있는 구매"가 0건이라, 아래 숫자는 이 정의에서도 그대로다.
- 구매 세션 = `purchase` 이벤트가 1개 이상 있는 세션(정상이든 아니든)이다.

| 판정 | 조건 |
|---|---|
| 정상 | 아래 조건에 해당하지 않음 |
| 경고 | 비율 ≥ 20% **그리고** 빈 구매 세션 ≥ 5개 |
| 차단 | 비율 ≥ 40% **그리고** 빈 구매 세션 ≥ 5개 |

근거:
- **운영 기간 56일의 하루 최대치는 14.3%**(1/17, 14세션 중 2개)이고, 대부분의 날은 0~8%다. 사고 첫날인 1/26은 60.8%(51세션 중 31개)다.
- **"5개 이상" 조건**은 구매가 적은 날 한두 세션 때문에 우연히 경고가 뜨는 것을 막는다.
- **이벤트가 아니라 세션 기준으로 센다.** 12/30은 이벤트 기준으로 37건 중 15건(41%)이었지만, 15건이 모바일 2세션(사용자 2명)에서 반복해서 찍힌 것이었다. 세션 기준으로는 9.5%(21세션 중 2개)라 정상이다.
- **20%와 40%는 초기값**이다. 근거와 함께 기록하고, 운영하면서 조정한다.

### 4.4 DQ1, DQ3, DQ4, DQ5 기준값 [정함, 2026-11-25]

DQ2와 같은 방법으로 정했다. 운영 기간의 하루하루 분포를 보고 평소 최대치와 알려진 사고 사이에 기준을 두었다. 값과 근거는 정의서의 "기준값 근거" 표에 있다.
- DQ1: 0건이면 차단, 7일 기준선 대비 0.3 미만이면 차단
- DQ3: 7일 기준선 대비 0.1 미만이면 경고 (기준선 20세션 이상)
- DQ4: 2% 초과면 경고
- DQ5: 25% 이상이고 5세션 이상이면 경고

연말 연휴에는 실제 방문이 7일 평균의 절반 이하로 떨어진다(구매 세션 최저 0.22). 그래서 DQ1과 DQ3은 "이벤트가 거의 사라지는 정도"만 잡게 했다.

### 4.5 빈 구매의 처리 [정함]

운영 기간 구매 세션 3,047개(기간 내 서로 다른 세션 기준) = 정상 주문이 있는 세션 2,907개 + 빈 구매만 있는 세션 140개
- 정상 주문이 있는 세션 2,907개 중 3개는 빈 구매도 함께 있다. 정상 주문이 빈 이벤트로 한 번 더 찍힌 중복으로 본다.
- **빈 구매만 있는 세션: 140개(4.6%)**. 이 중 139개가 결제 정보 입력까지 거쳤다. 실제 주문이 누락된 것으로 보인다.
- DQ2 분자(빈 구매가 1개 이상 있는 세션)는 143개다(140 + 3).

| 지표 | 빈 구매 세션 처리 |
|---|---|
| 세션 수, 상품 조회, 결제 시작 | 포함 |
| 주문 수, 매출, 객단가 | 제외 |
| 주문 전환율 | 분자에서만 제외 (분모의 세션에는 포함) |
| 퍼널 구매 세션 | 제외 (정상 주문이 있는 세션만) |
| 품질 체크 | DQ2에서 따로 센다 |

→ **주문과 매출은 빈 구매 때문에 실제보다 약 4~5% 과소 집계된다**고 정의서와 대시보드 각주에 밝힌다. 이 비율이 평소에 일정해서, 전주 대비나 7일 평균 같은 비교는 유효하다.

### 4.6 차단이 일어났을 때 (현업 대응 흐름)

1. **감지·공지**: 품질 게이트가 차단하면 알림을 보내고, 대시보드에 "검수 실패, 확인 중"을 띄운다.
2. **위치 판별**: 우리 SQL 문제인지(raw에는 값이 있음), GA4 export 문제인지, 웹 수집 문제인지(raw부터 비어 있음) 가린다.
3. **수정 요청**: 수집 문제라면 근거(기간, 비율, 빠진 필드)와 함께 수집 담당자에게 요청한다.
4. **복구**: SQL 문제라면 고친 뒤 그 날짜들을 Airflow로 백필한다. 수집 문제라면 GA4로는 복구할 수 없으니 `data_incidents`에 한 줄 추가하고 비교에서 뺀다. 주문 DB가 있다면 DB로 채운다.
5. **재발 방지**: 사고 기록을 남기고, 필요하면 체크를 추가한다.

## 6. 아키텍처

### 6.1 전체 흐름

```text
GA4 raw (public, 읽기 전용)
   │
   ▼  Airflow DAG (하루 1회, 데이터 날짜 1일 처리)
[1] raw 도착 확인 (DQ1)
[2] dbt build --vars run_date   모델 생성 + 테스트 (의존 순서대로)
       stg_events → f_orders, f_sessions → kpi_daily, kpi_weekly, dq_daily → 테스트
       error 테스트 실패 = 차단 → DAG 실패 → [3][4] 실행 안 함
[3] 대시보드 HTML 생성
[4] 게시
   실패 시: 알림 + "검수 실패" 화면 게시
```

### 6.2 BigQuery 위치 [제안]

- 프로젝트: `bigquery-457902` (이전 프로젝트와 같음)
- 새 데이터셋: `ga4_staging`, `ga4_mart`
- 기존 `ga4_ops_bi` 데이터셋과 `ga4-ops-bi` 폴더는 건드리지 않는다. GitHub Actions 버전의 비교 대상으로 남겨 둔다.

### 6.3 dbt 모델 [제안]

모든 모델은 날짜 파티션을 쓰고, 증분 방식은 `insert_overwrite`(그날 파티션만 교체)다.

| 모델 | 단위 (1행 =) | 주요 컬럼 | 용도 |
|---|---|---|---|
| `stg_events` | 이벤트 1건 | event_date, event_ts, user_pseudo_id, session_key, event_name, transaction_id, purchase_revenue, item_revenue 합, tax, device(데스크톱/모바일), session_number, is_empty_purchase | 배열을 한 번만 펼친다. 결함 구간을 포함해 전 기간을 보관한다 |
| `f_orders` | 주문 1건 | transaction_id, order_date, session_key, purchase_revenue, device, is_new_session | 담당자의 직접 분석용. 현업에서는 원천을 주문 DB로 교체할 자리다 |
| `f_sessions` | 세션 × 날짜 | session_key, session_date, device, is_new_session, has_view_item, has_add_to_cart, has_begin_checkout, checkout_with_cart, has_valid_order, has_empty_purchase, orders, revenue | 담당자의 직접 분석용. 퍼널의 원천이다 |
| `kpi_daily` | 날짜 × 구분 (전체 / 기기 / 신규·재방문) | 세션, 주문, 매출, 주문 전환율, 객단가, 퍼널 단계별 세션, 장바구니 담기율, 지난주 같은 요일 대비, 7일 평균 대비 | 대시보드용 |
| `kpi_weekly` | 주(월~일) × 구분 | 위와 같음. 세션은 그 주의 서로 다른 세션 수로 센다 | 대시보드용 |
| `dq_daily` | 날짜 × 체크 항목 | 값, 기준, 판정(정상/경고/차단), 진단 정보(기기·브라우저 분포, 사용자·세션 집중도) | 품질 게이트, 품질 화면 |
| seed `data_incidents` | 결함 구간 1개 | start_date, end_date, reason | KPI와 비교에서 자동 제외 |

규칙:
- 주문은 거래번호 1개 = 1건이다. 같은 거래번호가 여러 이벤트에 찍혔으면 **처음 찍힌 이벤트**를 쓴다. 같은 거래번호인데 매출 값이 다른 주문이 7건 있다.
- 거래번호가 여러 세션에 나타나면 **처음 나타난 세션**에 붙인다. 11/12~1/31에는 이런 거래번호가 15건이었다.
- **날짜를 넘는 중복 거래번호**: 운영 기간에 7건이 서로 다른 날짜와 세션에 걸쳐 찍혔다. [제안, 구현 규칙] 하루를 처리할 때 그날 안에서는 첫 이벤트만 쓴다. 그리고 이전 날짜의 `f_orders`에 이미 있는 거래번호는 뺀다(이전 파티션 대상 anti-join). 그러면 날짜 순서대로 돌리는 한 결과가 결정적이다. 그래서 `max_active_runs=1`로 날짜 순서를 지킨다.
- 세션은 이벤트가 있었던 날짜마다 1번씩 센다. 날짜를 넘긴 세션은 전체의 0.23%, 구매 세션의 1.7%다. 세션 집계는 그날 테이블 하나만 읽으면 된다.
- 세션 수의 기준은 두 가지다. 마트와 대시보드는 **세션 × 날짜**(운영 기간 230,471개, 구매 세션 2,903개)를 쓴다. 문서의 일부 근거 숫자는 **기간 내 서로 다른 세션**(정상 주문 세션 2,907개, 구매 세션 3,047개) 기준이다. 숫자 옆에 기준을 적어 두었다.

### 6.4 Airflow 실행 방식 [정함 + 미정]

- **[정함]** 앞부분은 백필로 한 번에 처리하고, 뒷부분은 매일 하루씩 실제로 돌린다. 로컬 Docker에서 실행한다.
- **[제안]** 하나의 DAG에서 시간을 고정 간격만큼 밀어서 대응시킨다.
  - `데이터 날짜 = Airflow 논리 날짜 − 고정 간격`
  - DAG를 켜면 지나간 날을 catchup으로 따라잡는다. 이게 백필이다.
  - 그다음부터는 매일 07:00 KST에 실행한다.
  - 백필과 라이브가 같은 코드로 돈다.
  - 대가로 날짜 변환 한 줄이 필요하다. 원본 테이블 이름과 `ds_nodash`가 그대로 일치하지 않기 때문이다.
- **[제안]** 실행은 날짜 순서대로 하나씩만 한다(`max_active_runs=1`). 비교 지표가 이전 날짜의 결과를 읽기 때문이다.
- 노트북이 꺼져 있어서 아침 실행을 놓치면, 다시 켰을 때 catchup으로 따라잡는다.
- **[정함]** 라이브 구간은 데이터 1/11~1/24의 14일이다. 11/30~1/10의 42일은 백필된다. 고정 간격 값은 실제로 DAG를 켜는 날에 맞춰 정한다.

### 6.5 대시보드 [정함 + 미정]

- **[정함]** 정적 HTML, Power BI 스타일, 웹에 게시한다.
- **[제안]** 위에서부터 §1.1의 세 질문 순서로 읽히게 구성한다.
  1. 오늘 볼 것: 매출과 비교(지난주 같은 요일, 7일 평균), 품질 상태(정상/경고/차단) 배너
  2. 어디서 변했나: 세션 × 주문 전환율 × 객단가 분해, 기기별, 신규/재방문별
  3. 세부: 퍼널(결제 시작 막대 분할), 장바구니 담기율, 주간 추세, 품질 화면(체크별 값과 진단 정보)
- 차단된 날은 KPI 대신 "검수 실패"를 보여 준다.
- 각주에는 "빈 구매로 주문·매출 약 4~5% 과소 집계", "퍼널 구매 세션 수 < 주문 수"를 적는다.
- **[정함]** 게시 위치는 GitHub Pages다.
- **[정함, 5단계]** 데이터 흐름: `dashboard/render.py`가 마트(`kpi_daily`, `kpi_weekly`, `dq_daily`)를 **직접 조회**해 정적 HTML을 만든다. CSV·JSON 사본은 만들지 않는다. 날짜별 HTML(`site/days/<date>.html`)과 git 이력이 "그날 게시된 숫자"의 기록이다. 현업에서도 자동 리포트는 웨어하우스를 직접 조회하고, 기록은 파일이 아니라 웨어하우스나 버전 이력에 남긴다.
- **[정함, 5단계]** 화면은 Power BI 보고서처럼 탭 3개로 나눈다.
  - **개요**: KPI 카드 5개와 매출 분해, 최근 4주 일별 매출
  - **퍼널 · 구분**: 기기·신규/재방문 표, 퍼널, 끝난 주의 주간 표
  - **데이터 품질**: 체크별 값·판정·진단, 각주
  - 품질 상태는 상단의 표시 하나로만 보여 주고, 누르면 품질 탭으로 간다. 경고일에만 개요에 배너가 뜨고, 차단일은 개요가 검수 실패 안내로 바뀌며 퍼널·구분 탭이 없어진다.
- **[정함, 5단계]** KPI 카드는 큰 값 → **▲/▼와 7일 평균 대비 한 줄** → 기준이 된 실제 값(7일 평균, 지난주 같은 요일) → 최근 14일 추세선 순서다. 비교할 날이 없으면 "비교 불가"로 표시한다.
- **[정함, 5단계]** 페이지 날짜 이후의 데이터는 절대 보여 주지 않는다. 추세는 그날까지만, 주간 표는 그날 이전에 끝난 주만 보여 준다.

## 7. 검증 계획 [제안]

| 단계 | 확인 방법 |
|---|---|
| 정의 | 이 문서에 적은 근거 숫자를 마트가 다시 만들어 내는지 확인한다. 운영 기간 기준으로 주문 3,232건, 매출 $221,762, 세션 230,471개, 퍼널(§3.2 표), 기기·신규 분해(§3.3 표). 작은 차이(날짜를 넘는 중복 처리 등)는 원인을 기록한다 |

| 백필·라이브 | catchup으로 백필 구간이 순서대로 처리되고, 라이브 구간이 매일 실행되는지 Airflow 실행 이력으로 확인한다 |

## 8. 운영 규칙 [제안, 설계 검토 후 추가]

설계 검토에서 나온 질문 중, 구현 전에 정해야 해서 제안으로 정한 것들이다.

| 항목 | 규칙 | 이유 |
|---|---|---|
| 파이프라인이 처리하는 날짜 | 예약 DAG는 운영 기간(11/30~1/24)만 처리한다 | 결함 구간은 게시 대상이 아니다 |
| staging의 결함 구간 | `stg_events`는 최초 1회 전 기간(11/1~1/31)을 full-refresh로 만든다. 이후 예약 DAG는 그날 파티션만 교체한다 | "raw와 staging에 보관" 원칙을 지키면서 DAG 범위는 깨끗하게 유지 |
| 1/26 사고 재현 테스트 | 운영 마트가 아닌 별도 dbt target(예: `ga4_mart_test` 데이터셋)에 수동 실행한다. 차단되고 "검수 실패"가 생성되는지 확인한다 | 운영 마트를 결함 데이터로 오염시키지 않기 위해 |
| DQ 기준값 계산 | 11/12~1/31 전체에 대한 일회성 분석 SQL(`analysis/` 폴더)로 분포를 보고 정한다. 근거는 정의서에 기록한다 | 사고 구간이 포함돼야 "평소 최대치와 사고 사이"를 잡을 수 있다 |
| 차단된 날 이후 | 다음 날짜는 계속 처리한다(`depends_on_past=False`). 차단된 날의 `kpi_daily` 파티션은 쓰되, `dq_daily`에 차단으로 기록한다. 그날 게시는 "검수 실패" 화면이다 | 하루가 막혀도 다음 날 대시보드는 나와야 한다 |
| raw 도착 확인 (구현 중 변경) | `check_raw`는 `BigQueryTableExistenceSensor`다. 10분마다 테이블을 확인하고(reschedule 모드라 기다리는 동안 작업 슬롯을 차지하지 않음), 6시간이 지나도 없으면 실패 → 검수 실패 화면을 게시한다. 테이블은 왔지만 비어 있는 경우는 DQ1이 잡는다 | 실제 GA4 export는 매일 도착 시각이 달라서, "없으면 바로 실패"가 아니라 "올 때까지 기다리고 기한을 넘기면 실패"가 맞다. Airflow에서 Sensor가 맡는 일이다 |
| dbt 실행 방식 (구현 중 변경) | Airflow에서 `dbt build` 하나가 아니라 `dbt run` → `dbt test` 두 작업으로 나눈다 | `dbt build`는 테스트가 실패하면 하위 모델(kpi_daily)을 건너뛴다. 그러면 "차단일도 KPI 파티션은 쓴다"가 지켜지지 않는다. 나누면 모델은 항상 쓰이고, 게이트는 `dbt test`의 실패로 판정된다 |
| 비교 기준에서 빼는 날 | `data_incidents` 구간과 `dq_daily`의 차단일 | |
| 지난주 같은 요일이 빠진 날일 때 | 비교값을 비우고 "비교 불가"로 표시한다. 다른 날로 대체하지 않는다 | 대체 규칙은 해석을 복잡하게 만든다 |
| 7일 평균 | 직전 7일(달력 기준) 중 유효한 날만 평균한다. 유효한 날이 5일 미만이면 비운다 | |
| DQ1·DQ3의 기준선 | 위 7일 평균과 같은 규칙이다. 유효일 5일 미만인 운영 기간 첫 5일(11/30~12/4)은 "기준 부족"으로 둔다. DQ1의 "미도착"은 기준선 없이 항상 판정한다 | 11월 결함 구간을 기준선으로 쓰지 않기 위해 |
| 매출 값 | `purchase_revenue`를 그대로 쓴다. 세금을 따로 빼지 않는다 | 운영 기간 주문 매출($221,762)과 상품 매출 합($221,661)이 거의 같다. 즉 이 값에는 세금($18,661)이 들어 있지 않다 |
