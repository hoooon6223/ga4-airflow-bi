# 사고 기록: 2021-01-26 주문 정보 누락 (재현)

작성일: 2026-11-26
성격: 운영 기간 밖의 실제 수집 결함을 테스트 데이터셋(`ga4_mart_test`)에 다시 흘려, 품질 게이트가 사고를 잡는지 확인한 기록이다. 현업이었다면 이 형식으로 사고를 남긴다.

## 요약

| 항목 | 내용 |
|---|---|
| 무엇이 | 구매 이벤트는 찍혔지만 거래번호·매출·상품 정보가 모두 빠짐 |
| 언제부터 | 2021-01-26 (구매 세션의 60.8%) → 1/31 100% |
| 어떻게 잡았나 | DQ2 "거래번호 없는 구매 세션 비율" 60.8% ≥ 40%, 해당 세션 31개 ≥ 5 → **차단** |
| 대시보드 | KPI 대신 "검수 실패" 페이지 게시. 담당자에게 "이 날 수치를 의사결정에 쓰지 말 것" 안내 |
| Airflow | `dbt_test` 실패 → KPI 화면 생성 건너뜀 → 검수 실패 화면 생성 → 실행은 빨간색으로 남음, 실패 알림 2건 |
| 원인 위치 | 웹 수집(추적 코드). raw 이벤트부터 값이 비어 있음 (우리 SQL 문제 아님) |
| 복구 가능성 | GA4로는 불가 (지나간 이벤트는 재수집되지 않음). 주문 DB가 있었다면 DB로 채움 |

## 1. 감지 (그날 아침)

품질 게이트(`dq_daily`)가 1/26을 이렇게 판정했다.

| 체크 | 값 | 판정 |
|---|---|---|
| DQ1 이벤트 총량 (7일 기준선 대비) | 89.5% (42,232 / 47,202) | 정상 |
| **DQ2 거래번호 없는 구매 세션 비율** | **60.8% (31 / 51)** | **차단** |
| DQ3 조회 / 장바구니 / 결제 / 구매 세션 (7일 기준선 대비) | 97% / 79% / 84% / 86% | 정상 |
| DQ4 주문 매출 대사 | 0.08% | 정상 |
| DQ5 다중 주문 세션 비율 | 4.8% | 정상 |

- 이벤트 양이나 퍼널 단계별 세션 수는 평소와 다르지 않았다. **그래서 "구매가 줄었다"가 아니라 "구매는 있었는데 주문 정보가 사라졌다"는 신호다.**
- 이 사고는 DQ2만 잡는다. DQ1·DQ3(양의 급감)으로는 보이지 않는 유형이다.

## 2. 위치 판별

| 확인 | 결과 | 판단 |
|---|---|---|
| raw(`events_20210126`)의 구매 이벤트에 값이 있나 | 거래번호 `(not set)`, `purchase_revenue` null, 상품명 `(not set)`, 가격·수량 null | raw부터 비어 있음 → **우리 파이프라인 문제 아님** |
| 특정 기기·브라우저에 몰렸나 (DQ2 진단 정보) | 사용자 31명·세션 31개, 데스크톱 15·모바일 16, `<Other>`·Chrome·Firefox·Safari | 여러 기기·브라우저에 고르게 퍼짐 → **사이트 전체의 추적 코드 문제** |
| 실제 구매였나 | 1/26~1/31 빈 구매 세션 210개 중 209개가 결제 정보 입력(`add_payment_info`)을 거침 | 결제 과정은 정상 → **실제 주문인데 정보만 유실**된 것으로 보임 |
| 하루짜리인가 | 1/27 82%, 1/28 91%, 1/31 100% | 며칠 이어지는 결함 (그날 아침에는 알 수 없음 — 그래서 판정은 그날 숫자만으로 함) |

참고: 12/30에도 빈 구매 이벤트가 37건 중 15건이었지만, 모바일 2세션(사용자 2명)에서 반복해 찍힌 것이었다. 세션 기준으로는 9.5%라 정상이다. 이벤트가 아니라 세션으로 세는 이유다.

## 3. 수집 담당자에게 보낼 요청 (예시)

> 1/26부터 `purchase` 이벤트의 `transaction_id`, `value`(purchase_revenue), `items`가 비어서 들어옵니다.
> 구매 세션 중 비율은 1/26 60.8% → 1/27 82% → 1/31 100%입니다. 기기·브라우저 구분 없이 발생합니다.
> 결제 정보 입력(`add_payment_info`)까지는 정상이라, 결제 완료 시점에 주문 정보를 보내는 부분이 깨진 것으로 보입니다.
> 1/25~26 사이 결제 완료 페이지나 태그 관리자(GTM) 배포 내역 확인 부탁드립니다.

## 4. 복구

- **이미 지나간 날**: GA4는 다시 수집할 수 없다. `dbt/seeds/data_incidents.csv`에 구간을 추가했다(`INC-2021-01`, 1/25~1/31). 이 날들은 KPI 비교 기준(지난주 같은 요일, 7일 평균)에서 자동으로 빠진다. 주문 DB가 있었다면 이 기간의 주문·매출을 DB 기준으로 채우고 Airflow로 백필한다.
- **수집이 고쳐진 뒤**: 새 데이터가 정상으로 들어오면 게이트를 자동으로 통과해 평소대로 게시된다.
- **놓치기 쉬운 점**: 1/26이 결함일이면, 일주일 뒤 2/2의 "지난주 같은 요일" 비교도 깨진 날을 기준으로 삼게 된다. 결함 목록과 차단일을 비교에서 자동으로 빼는 이유다.

## 5. 재발 방지

- DQ2를 세션 기준으로 매일 판정한다 (이미 운영 중).
- 추적 명세(어떤 이벤트에 어떤 값을 보내는지)를 문서로 두고, 배포 전에 구매 이벤트 페이로드를 검수한다.
- 같은 유형이 11/1~11/11에도 있었다(거래번호만 누락, 매출은 있음). 그래서 DQ2 분자는 "매출 유무와 관계없이 거래번호가 없는 구매"로 정의했다.

## 재현 방법

```bash
# Airflow (테스트 데이터셋에만 쓰고, 실제 사이트에는 게시하지 않음)
docker compose exec airflow-scheduler airflow dags trigger ga4_ops_daily \
  --conf '{"data_date": "2021-01-26", "target": "test"}'
```

결과: `dbt_test` failed → `render_ok` upstream_failed → `render_blocked` success → `publish`(테스트라 게시 안 함) → `gate_result` failed. 검수 실패 페이지는 `airflow/logs/site_test/days/2021-01-26.html`에 생성된다.
